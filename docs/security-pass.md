# Security pass (v2)

What was checked, what was found, and what was fixed, for the v2 submission. Checked on November 20, 2026, against the production Supabase project and the `v2-design` branch.

## 1. The course checklist

| Check | How it was checked | Result |
| --- | --- | --- |
| Every API route that reads or changes someone's data checks who's signed in | Read every route under `src/app/api/` | Import start and step require a Clerk session (401 otherwise) and act only on the caller's rows through RLS. Discogs search, release, and tracklist routes don't touch user data (public Discogs data, rate-limited per user or per IP). `/api/demo` serves a public collection. `/api/cron/keepalive` requires `CRON_SECRET`. `/api/webhooks/clerk` verifies Clerk's signature and needs a second secret to delete anything. Everything else the browser reads or writes goes to Supabase with the Clerk session token, so RLS applies. |
| Every Supabase table has a grant and row level security | Read-only query on `pg_class`, `pg_policies`, and table privileges | All 11 tables have RLS on (13 before the tags and artist tags tables were dropped), four own-row policies (select, insert, update, delete on `auth.jwt()->>'sub' = user_id`), grants to `authenticated` only, and no access for `anon`. |
| One account can't see another's data | `npm run test:rls` (two real Clerk test users, the real Data API) | 46 checks pass, including every v2 table (temporary locations, preferences, guest links), the RPCs, the limits added after the independent review (§4), and that the removed tags are gone (no table, no tag sort level, no tag section). |
| Keys out of the repository; agents kept out of `.env` | Secret scan of tracked files; `.gitignore`; `.claude/settings.json` | No keys or tokens in tracked files. `.env*` is gitignored. | If the app calls a model, a rate limit and a token cap | — | The app calls no AI model. |

## 2. Database functions

| Function | Who can call it | Why it's safe |
| --- | --- | --- |
| `save_setup`, `apply_placements` | `authenticated` | Security invoker: RLS applies; they refuse without a session. |
| `shared_shelf(token)` | `anon`, `authenticated` | Security definer, on purpose: returns one shelf only for an active, unguessable token (128 random bits), only the fields the read-only view needs; null otherwise. Revocable. |
| `delete_user_data(user_id, secret)` | `anon`, `authenticated` | Security definer, on purpose (the Clerk webhook has no session): refuses unless the secret's SHA-256 matches the one in `private.settings`, which the Data API doesn't expose. |
| `keepalive()` | `anon` | Returns 1, for the daily cron. |
| `private.purge_inactive_discogs_data` | nobody through the API | Run nightly by `pg_cron`. |
| `classify_*` | `authenticated` | Pure classification; the format-group trigger calls them as the inserting user. Not callable by `anon` (§4, finding 8). |
| `records_fill_format_group`, `enforce_row_quota`, `prune_layout_events`, `import_jobs_limit_starts`, `import_jobs_forward_only` | nobody through the API | Trigger functions (EXECUTE is checked when a trigger is created, not when it fires). |

## 3. What was found and fixed during the pass

1. **`anon` could execute `save_setup` and `apply_placements`.** Supabase grants EXECUTE to `anon` on new functions by default, and v1 only revoked it from `PUBLIC`. Both functions already refused without a session and ran under RLS, so no data was exposed. Fixed in `20261120111930_v2_function_grants.sql`; the RLS test now checks that anonymous calls to `save_setup` fail.
2. **Database error messages reached the browser on import failures.** Fixed: import routes return a generic sentence for server errors and log the details (`src/lib/import/errors.ts`).
3. **No Content-Security-Policy.** Fixed: a policy tuned for Clerk (its Frontend API, Clerk Protect on any port, the Cloudflare check), Supabase, and Discogs covers, with `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'self'`, and `form-action 'self'`. Checked in a browser with no violations (sign-up, demo, covers, tracklists). It still allows inline scripts, which Next.js and the language script need; a nonce-based policy would remove that.
4. **Discogs data kept forever for accounts that stopped using the app.** Fixed: a nightly `pg_cron` job deletes records of accounts that haven't synced in 90 days.
5. **Deleting a Clerk account left its rows.** Fixed in code and in the database; it needs Ale to set two environment variables, store the secret's hash, and add the webhook endpoint in Clerk (steps in `docs/v2-design-log.md`, "Blocked: needs Ale").

## 4. Independent review

A fresh session reviewed the whole project for security problems (instructions: read-only, most serious first, how to verify each fix). It read every migration, all of `src/`, the config, and the scripts. **It found no way for one account to read or change another's data, no way for an anonymous caller to write anything, and no leaked secrets.** Its findings were about availability, defense in depth, and the Discogs data rules. What was done about each:

| # | Finding | Severity | What was done | How it was verified |
| --- | --- | --- | --- | --- |
| 1 | Anyone could use up the app's single Discogs token (60 requests a minute): three anonymous routes allowed 15 calls a minute per IP each, the limiter is per server instance and keyed on whole IPv6 addresses, the import step allowed 120 a minute, and a 429 was retried three times | Medium | The budget is split: imports slow down when Discogs reports fewer than 30 requests left (2.5 s between steps, growing to about 14 s as the budget runs out, so several imports at once settle above what searches need); searches, releases, and tracklists wait up to 5 s while the estimated budget (the last reading plus one request a second) is below 10, are refused without calling Discogs if it would take longer, and are never retried, so they can't starve imports; imports keep their backoff. The import step allows 50 a minute. The refresh at the end of a sync stops when the budget is low. (Two earlier versions failed the e2e suite, which runs several real imports in parallel: a fixed reserve for imports let imports starve searches, and a low reading blocked searches for a whole minute. Hence the pacing, the refill estimate, and the short wait.) Anonymous visitors are counted by their IPv6 /64 network (`src/lib/discogs/client.ts`, `src/lib/rate-limit.ts`) | Vitest with a mocked `fetch`: straight through above the floor, a short wait just under it, refused without calling Discogs when the budget is gone and open again after the refill, imports go on, no interactive retry, import retries with backoff, and the import pause grows as the budget shrinks; the full e2e suite (parallel imports and searches); IPv6 keys share one /64 (compressed, bracketed, zoned, IPv4-mapped) |
| 2 | Any signed-in user could fill the free 500 MB database (unbounded `layout_events.moves`, no per-account row limits, compartments at any row and column), which turns the project read-only for everyone | Medium | Migration `20261120113954_v2_security_review`: `moves` at most 1 MB per row, style and format text at most 2,000 characters, compartments inside a 12 × 24 shelf, per-account quotas (25,000 records, 30 shelves, 100 temporary places, 20 guest links; the tags and artist tags quotas went with those tables), and a layout log that keeps each account's newest 500 events (up to 5 MB) and always its newest calibration. | 5 | Supabase Auth's own email sign-up is enabled (checked: `disable_signup: false`, auto-confirm on), so anyone can get an `authenticated` token without Clerk | Low | Migration `20261120114356_v2_clerk_user_ids`: every table requires a Clerk-shaped `user_id` (`user_…`), so a Supabase Auth token (a uuid `sub`) can't write anything. Turning sign-ups off is a dashboard setting: **on Ale's list** | Read-only query: a validated constraint on every table (13 then, 11 after tags were removed); no existing row and no Supabase Auth user were affected (0 of each); the RLS and e2e tests (Clerk users) still pass |

**A mistake made and fixed during this pass.** The first version of the layout-log trigger used `old` as a subquery alias, which clashes with PL/pgSQL's `OLD` record, so every insert into `layout_events` failed. The extended RLS test caught it about three minutes after the migration was applied; `20261120114224_v2_fix_layout_prune` fixed it. A failed insert rolls back its whole transaction (`save_setup` and `apply_placements` write everything in one), so no partial change was saved; a map change made in those minutes would have shown an error.

**Still open, for Ale:** turn off Supabase Auth sign-ups (Authentication → Sign In / Providers: "Allow new users to sign up" off and the Email provider off; Clerk stays as the third-party provider, and its tokens don't go through Supabase Auth, but sign in once afterwards to check), configure the Clerk deletion webhook, and decide on a Clerk production instance and a separate database for tests.
